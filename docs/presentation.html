Presentation notes

Cognitive-twin tutor

A tutor for any topic that remembers what each student gets wrong, teaches the next lesson a different way, and knows when to stop and ask. Code decides what happens next. The model only writes.

  • 493 automated tests
  • 4 languages, 17 versions, in a locked-down code sandbox
  • The answer key never leaves the server
  • Runs fully offline on a scripted model
  • Built on the Agentic Slice Kit

If you only get 30 seconds

Chat assistants explain, but they do not remember. Our tutor keeps a cognitive twin of every student: what they know, how well, how recently, and which specific wrong ideas they hold. Every wrong option in a quiz is written to stand for one wrong idea, so a wrong answer does not just say "wrong", it names the misunderstanding. The tutor then goes back and teaches the same topic a different way, aimed at that idea, and remembers it next week.

The problem

A correct explanation that never fixes the belief

A student asks a chat assistant why a Python function's list default "keeps growing". The answer is correct and fluent. The student nods.

Three weeks later, in a lab test, they write def add(item, bucket=[]) again. They came away believing the default is copied fresh on every call, and the explanation never touched that belief. Nothing in their history said they had held it before.

From demo/tutor/TUTOR-SPEC.md, section 2.

Three gaps in a general chat assistant

  1. No memory of you. It cannot tell that this student keeps believing the same wrong thing, so it explains the same way each time.
  2. It cannot name the belief. "Wrong" is not a diagnosis.
  3. Its source is the whole internet. The student cannot tell what their own teacher would accept.

What it does

A student's session, in six steps

  1. Sign inAn account with a name and a password. Progress and documents belong to that account only.
  2. Say what to learnAny topic in the student's own words, or paste an exam question. Optionally attach their teacher's notes as the source of truth.
  3. It plansWhat the topic builds on, and its parts. A concept map shows the route.
  4. It checks before it explainsA quick question on each prerequisite. Right: skipped. Wrong or "I don't know": taught.
  5. Explain, then checkA short lesson. The student chooses: quiz me, another example, more detail, go deeper, skip. The check is multiple choice, own words, or a program. They say how sure they are.
  6. Final checkOne written question that needs several parts at once. Then the twin is updated and the day counts towards their streak.

Also in the box

The twin, in plain view

A Twin tab shows what the tutor believes about the student and which wrong ideas it is watching. Nothing is hidden.

Their own notes, with citations

Teach only from the student's documents, citing them. A topic the notes do not cover is not guessed: the student chooses.

Confidence counts

"Just guessing", "Fairly sure", "Certain". Certain and wrong costs the most. "I don't know" is honest, never a wrong belief.

A code sandbox

Run your own code beside any lesson in Python, JavaScript, Java or C++. Program questions are graded on hidden tests.

Streak and activity heatmap

A 🔥 streak and a year-long heatmap, worked out from records that already exist. Nothing extra is stored.

Sign-in that keeps students apart

Hashed passwords, and every session and document is locked to its owner.

Architecture

How it fits together

Read the picture top to bottom. The student never talks to the model directly. Everything passes through one loop, and the loop only acts on what the database says.

One answer, end to end

  1. 1The student answers in the browser (or asks for an example). The page only ever received the question, never the answer key.
  2. 2The API checks who they are and drops the answer into the run. It does not grade anything itself.
  3. 3The loop wakes up from the database. It grades: multiple choice by plain code, a program by hidden tests in the sandbox, an own-words answer by the model against a rubric.
  4. 4Code updates the twin and decides what is next: another prerequisite, re-teach this topic in a different style, the next part, the final check, or stop.
  5. 5Everything is saved, the model writes the next lesson, and the loop suspends to ask the student. Back to step 1.

Three design choices to point at

State lives in the database

Not in a chat window, not in the process. Restart the server mid-lesson and the run resumes. The history is append-only, so any run can be replayed.

Code decides, model writes

Which step comes next, how mastery moves and when to stop are ordinary functions. The model is used where judgement or language is needed, inside a step.

Every boundary is typed

Model replies are parsed by schemas. A bad reply gets one repair pass, then the fallback model, then a visible, honest failure.

Why it is agentic

A workflow that can go backwards

The organisers' own test: "an agent is a workflow that can go backwards." Straight through A, B, C is a pipeline, however many models are in it. Ours sends work back, and where it goes next depends on what the student's answer showed.

The agentic part, in one paragraph

The heart is a single loop over the student's twin: read the twin, decide the next step, act, suspend to ask the student, update the twin, repeat. It is a real state machine (DRAFTING, GATING, AWAITING_EXPERT, COMPLETE, FAILED), it persists between steps and between sessions, it calls tools (note search, the code sandbox), it stops and waits for a human, and it goes backwards when an answer shows a wrong idea. Which topic, which style and when to stop are decided by code, so the behaviour is bounded, reviewable and testable.

Where the agent lives in the code

slice/runner.py

The state machine, from the kit: moves a run between states and resumes it. It knows nothing about tutoring.

demo/tutor/flow.py

Ours. Two handlers: handle_drafting (choose and write the next step) and handle_gating (grade the answer, update the twin).

demo/tutor/steps.py

The policy as pure functions: decide picks probe, teach, final or done from the plan, the twin and this session's checks.

demo/tutor/learner.py

The twin's arithmetic: apply_check, effective_mastery (forgetting), style_for (the next teaching style).

What is deliberately not agentic

The model never chooses its own next action and never calls a tool by itself. That is a choice, following the kit's principle "orchestration in code, judgement in the model": a model that picks its own next step has unbounded cost and a control flow that is different every run, so it cannot be audited afterwards. Say it plainly: ours is bounded, stateful orchestration, where the route depends on what the student's answers show.

Seven things to point at

1. Diagnostic distractors

A wrong option is not random noise. It is written to be the one wrong idea a student would hold. A wrong pick is a diagnosis.

2. A twin that forgets

Mastery slides back toward "unknown" over time, so the tutor brings a topic back when it is due, from what the student knows now, not their peak.

3. Probe before explain

It tests a prerequisite before teaching it, so a student is never re-taught what they already know.

4. Honest gaps

With the student's notes on, it cites them and says "not in your documents" instead of guessing.

5. Confidence-calibrated scoring

How sure a student was changes how far the answer moves the score, and a certain wrong belief counts double.

6. Questions that check themselves

A program question is only shown once the model's own solution passes its own hidden tests in the sandbox. Otherwise it is rewritten, then replaced by multiple choice.

7. Nothing leaks

The answer key and hidden tests never reach the browser. Each student's sessions and documents are theirs alone.

Expect these

Judge questions, with honest answers

Isn't this just a prompt wrapped in a chat interface?

No. The model writes lessons and questions, but it does not run the session. A state machine does, over a database. The twin persists across sessions, the run suspends and resumes, tools are called, and the route goes backwards depending on the answers. The prompts are the smallest part of it.

Who decides what happens next: the model?

Code does, on purpose. steps.decide is a pure function over the plan, the twin and this session's checks. It is tested in microseconds. The model never picks its own next action, because that would make cost unbounded and behaviour different every run. That is the kit's own principle: orchestration in code, judgement in the model.

Show me where it goes backwards.

Three places, all in demo/tutor/flow.py. A wrong answer returns from grading to teaching with a new style aimed at that idea. A failed final check re-teaches the weakest part, at most twice. A program question whose own solution fails its own tests is rewritten once with the reason fed back, then replaced by multiple choice.

What if the model writes a wrong question or bad tests?

For program questions we run the model's own solution against its own hidden tests in the sandbox before the student sees the question. Model replies are also parsed by schemas, with one repair pass and a fallback model. For multiple choice we cannot prove a distractor names exactly one belief. We saw it hold on a handful of live lessons and have not tested it widely.

What stops it looping forever or burning tokens?

Two kinds of limit that do not share a counter. A spend limit (250,000 tokens per run by default, and attempts per step) and revision limits counted from the record history: 16 checks, 30 steps, 2 explanations in a row, 2 revisions after a failed final. The revision limits live in code, not in a prompt.

What if the student walks away, or the server restarts?

The run is a suspended state in the database, so nothing is lost. The page resumes an interrupted session on reload. If nobody answers within 24 hours the session ends as "student left". A missing-notes question that times out counts as a skip, never as consent.

Can a student see the answers, or another student's data?

The answer key, rubric and hidden tests never leave the server, and there are tests that read the network payloads for them. Every session and document is locked to its owner: another student's run answers "no such session". Names that existed before accounts are locked so nobody can take over their progress by signing up first.

Is running a student's code safe?

Each run is a throwaway Docker container: no network, read-only root, all capabilities dropped, non-root, memory, CPU, process and time limits. The source and test inputs go in as base64, never on a command line. Each language and version is proven on first use and fails closed. One honest gap: a process running as the same user can still read /proc/1/environ, so a determined student could read the hidden test inputs.

How do you know students learn more?

We do not. There is no before-and-after test and no comparison with a plain chat assistant. What we can show is that testers were heard and the tool changed quickly. A quick way to get real evidence: ask a tester three questions cold, let them use the tutor for about 15 minutes, then ask three different questions on the same topic.

Where do the numbers come from: 75%, 14 days, 0.3 / 0.5 / 0.6?

They are our guesses, not calibrated on real students, and we say so in the spec. We also cannot tell whether students report their confidence honestly. A student who always taps "Certain" is not fooled by it, because a wrong certain answer costs the most, but nothing here measures it yet.

Does the model hallucinate?

General-knowledge lessons cannot be checked against anything, so they carry a visible label and an instruction to leave out what the model is unsure of. In notes mode, every citation is checked in code against what retrieval returned, and a lesson that cites nothing it was given fails instead of being shown.

Does it work for subjects other than programming?

Topics are free text, the prompts are subject-neutral, and the code sandbox is optional beside every lesson. A live check on "photosynthesis" produced a clean lesson and plan with no code in either. Most of our testing has been on programming topics, so say that if asked.

What did you build, and what did the kit give you?

The kit gave us the spine in slice/: the state machine, the store, the callback, the budget and the model client. We built the whole tutor on top of it: the learner model, guided planning, probes, grading, the code coach and sandbox, the API, sign-in, the interface, and the tests.

What does it cost to run?

A free OpenRouter key is enough (the team's report; not independently checked). A lesson uses about 1,400-1,600 tokens. We measured latency but not free-tier rate limits, so say that if asked. Docker is only needed to run code.

What is next?

A second round with the same testers and a before-and-after measure, calibrating the mastery constants on real sessions, a teacher dashboard, separate mastery per language, and testing with a real teacher's PDFs and slides.

Be honest about

Known limits

Not calibrated

The mastery constants (75%, 14 days, the confidence weights) are guesses. Whether students report confidence honestly is not measured.

No learning-gain measurement

Outside-user evidence is real but thin: three named testers and no second round.

General knowledge is unchecked

Lessons without notes cannot be verified. They are labelled, not proven.

Sandbox limits

Four languages, single-file programs, no interactive input, runtimes pulled once. A same-user process can read /proc/1/environ.

Mastery is shared across languages

Knowing recursion in Python counts when you switch to Java. Per-language mastery is not built.

Not verified

Free-tier rate limits, real teacher PDFs, Codespaces, and diagrams offline (Mermaid loads from a CDN).

Not built

A teacher dashboard, email (a forgotten password is reset by whoever runs the server), and a second round of user testing.
